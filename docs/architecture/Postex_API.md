# مستندات جامع و راهنمای یکپارچه‌سازی وب‌سرویس پستکس (Postex API)

این سند مرجع یکپارچه‌سازی سامانهٔ **ByeMoney** با وب‌سرویس شرکت **پستکس (Postex)** بر اساس مشخصات رسمی **OpenAPI 3.1.1** پستکس است و نگاشت‌های اختصاصی معماری تسک‌های `SHIP-TRACKING` و `SHIP-TRACKING-B` را در بر دارد.

---

## ۱. مشخصات عمومی و زیرساخت (Specifications & Architecture)

- **نگارش استاندارد:** OpenAPI 3.1.1
- **آدرس پایه محیط عملیاتی (Base URL):** `https://api.postex.ir/`
- **فرمت تبادل داده:** تمام درخواست‌ها و پاسخ‌ها در قالب `application/json` با انکودینگ `UTF-8` هستند.
- **احراز هویت (Authentication):**
  احراز هویت در تمام اندپوینت‌های اختصاصی از طریق هدر HTTP زیر صورت می‌پذیرد:
  ```http
  x-api-key: <YOUR_POSTEX_API_KEY>
  Content-Type: application/json
  Accept: application/json
  ```
  > [!NOTE]
  > در ماژول `PostexIntegration` بای‌مانی، کلید دسترسی از طریق متغیر محیطی `POSTEX_API_KEY` و آدرس پایه از متغیر `POSTEX_BASE_URL` خوانده می‌شود تا هیچ کلیدی در سورس‌کد ذخیره نشود.

### ۱.۱. رفتار واقعی احراز هویت و قالب خطا (سنجیده‌شده)

- نام هدر `x-api-key` در سند رسمی نیامده بود؛ از پاسخ خطای سرویس استخراج شد و با ارسال کلید نامعتبر تأیید شد (پیام خطا از «کلید ارسال نشده» به «کلید نامعتبر» تغییر می‌کند).
- اندپوینت‌های `common` و `locality` **بدون کلید** هم پاسخ ۲۰۰ و کامل می‌دهند. بقیهٔ اندپوینت‌ها بدون کلید `401` می‌دهند.
- قالب بدنهٔ خطا `PascalCase` است، برخلاف `snake_case` اکثر پاسخ‌های موفق:

  ```json
  {"IsSuccess":false,"Message":"No API key was provided. Please include a valid API key in the request headers."}
  ```

- پیام کلید نامعتبر: `The provided API Key is not vlaid.` (غلط املایی خود سرویس؛ برای تشخیص خطا روی متن تکیه نکنید).

## ۲. سرویس‌های پایه و تعاریف سیستم (Common APIs)

این سرویس‌ها اطلاعات پایه برای ثبت مرسوله، ابعاد بسته‌بندی، روش‌های پرداخت و وضعیت‌ها را بازمی‌گردانند.

| ردیف | متد | مسیر (Route) | شرح عملیات |
| :--- | :--- | :--- | :--- |
| ۱ | `GET` | `/api/v1/common/shipping-methods` | دریافت فهرست کوریرها و شیوه‌های ارسال فعال (هجده سرویس؛ فهرست واقعی در بند ۹.۳) |
| ۲ | `GET` | `/api/v1/common/boxes` | دریافت ابعاد و انواع جعبه‌های استاندارد پستی مجاز برای بسته‌بندی |
| ۳ | `GET` | `/api/v1/common/payment-methods` | دریافت شیوه‌های مجاز پرداخت کرایه (پیش‌کرایه، پس‌کرایه/COD) |
| ۴ | `GET` | `/api/v1/common/statuses` | دریافت فهرست کامل وضعیت‌ها و رویدادهای مرسوله |

## ۳. تقسیمات مکانی و استانی (Locality APIs)

جهت تعیین کد شهر مبدأ و مقصد در استعلام هزینه و ثبت مرسوله:

| متد | مسیر (Route) | پارامترها | شرح |
| :--- | :--- | :--- | :--- |
| `GET` | `/api/v1/locality/provinces` | - | لیست استان‌ها |
| `GET` | `/api/v1/locality/cities/all` | - | لیست تمام شهرهای پشتیبانی‌شده |
| `GET` | `/api/v1/locality/cities/{province-code}` | Path: `province-code` | لیست شهرهای یک استان خاص |
| `GET` | `/api/v1/locality/cities/from/all` | - | لیست تمام شهرهای مجاز به عنوان مبدأ جمع‌آوری |
| `GET` | `/api/v1/locality/cities/to/all` | - | لیست تمام شهرهای مجاز به عنوان مقصد توزیع |

> [!IMPORTANT]
> نام این مسیرها گمراه‌کننده است: `cities/from/all` و `cities/to/all` هر دو فقط **۱۰ شهر پرکاربرد** را برمی‌گردانند (خروجی هر دو کاملاً یکسان است). فهرست کامل ۲۷۰۱ شهر فقط از `cities/all` (ساختار تودرتوی استان ‌→ شهرها) یا `cities/{province-code}` (ساختار مسطح) به دست می‌آید. جزئیات در بند ۹.۷.

## ۶. رهگیری وضعیت و استعلام رویدادها (Tracking & Events)

برای پایش خودکار وضعیت ارسال کالا در سامانه ByeMoney، مسیرهای زیر در دسترس هستند:

### ۶.۱. استعلام وضعیت تکی با شناسه مرسوله
- **مسیر:** `GET /api/v1/parcels/{parcel-no}/status`
- این مسیر پیش‌فرض مورد استفاده در کلاینت `PostexTrackingClient` است.

### ۶.۲. استعلام گروهی وضعیت مرسولات
- **مسیر:** `POST /api/v1/parcels/statuses/query`
- **بدنه درخواست:**
  ```json
  {
    "parcel_no": [10001, 10002, 10003]
  }
  ```

### ۶.۳. رهگیری رویدادها با بارکد و شرکت حمل‌کننده
- **مسیر:** `GET /api/v1/tracking/events/{courier}/{tracking-code}`
- برای مرسولاتی که شناسه داخلی پستکس ندارند و فقط شرکت پستی (مثل `IR_POST` یا `CHAPAR`) و شماره بارکد پستی را دارند.

### ۶.۴. رهگیری رویدادها با شناسه مرسوله
- **مسیر:** `GET /api/v1/tracking/events/{parcel-no}`

### ۶.۵. گزارش تغییر وضعیت‌های مرسولات در بازه زمانی
- **مسیر:** `GET /api/v1/tracking/report?from_date=2026-11-01&to_date=2026-11-15`
- **محدودیت واقعی:** بازه نباید بیش از ۷۲ ساعت باشد؛ بازهٔ بزرگ‌تر پاسخ `400` با پیام «بازه گزارش گیری نمی تواند بیشتر از 72 ساعت باشد» می‌دهد.
- **ساختار پاسخ بازگشتی:**
  ```json
  [
    {
      "order_no": 12345,
      "tracking_no": "194820011223344",
      "change_status_date": "1405/08/24",
      "change_status_date_utc": "2026-11-14",
      "change_status_time": "14:32:00",
      "change_status_time_utc": "11:02:00",
      "event_code": "DELIVERED",
      "event_name": "DELIVERED",
      "event_desc": "مرسوله به گیرنده تحویل داده شد",
      "custom_order_no": "BM-ORD-77492-ITM-1",
      "custom_reference_no": null
    }
  ]
  ```

### ۶.۶. رویدادهای وب‌هوک (Webhooks)
- `GET /api/v1/events`: فهرست رویدادهای سیستم
- `GET /api/v1/events/{eventId}`: جزئیات یک رویداد وب‌هوک خاص
- `GET /api/v1/parcels/{parcelNo}/events`: رویدادهای مربوط به یک مرسوله خاص

## ۷. مقادیر ثابت و شناسه‌ها (Enums & Constants)

### ۷.۱. روش‌های جمع‌آوری (`collection_type`)
- `pick_up`: درخواست جمع‌آوری از محل فرستنده (انبار طلا).
- `courier_drop_off`: تحویل حضوری فرستنده به باجه شرکت پستی انتخابی.
- `postex_drop_off`: تحویل حضوری فرستنده به دفاتر پستکس.

بای‌مانی روش را از همان درخواست ادمین می‌گیرد، نه از تنظیم سراسری. «پیک بیاید» یعنی `pick_up` با `ready_to_accept=true` و مختصات مبدأ. «تحویل به باجهٔ پست» یعنی `courier_drop_off`، بدون اعلام پیک، بدون شناسهٔ دفتر و بدون الزام مختصات. اگر پستکس این حالت را به‌خاطر نبود شناسهٔ دفتر رد کند، پیام دامنه برمی‌گردد و فهرست دفتر ساخته نمی‌شود.

### ۷.۲. کدهای سرویس‌دهنده پستی (`courier.name` / `courier_code`)
فهرست زیر از پاسخ واقعی `GET /api/v1/common/shipping-methods` استخراج شده و جای لیست حدسی قبلی را می‌گیرد. هفت `courierCode` فعال وجود دارد:

- `IR_POST`: شرکت ملی پست (سرویس‌های `EXPRESS`، `PRIORITY`، `POSTEXPRESS`، هر سه با ۱۰٪ مالیات)
- `CHAPAR`: چاپار (سرویس `CHAPAR`)
- `DEKAPOST`: دکاپست (سرویس‌های `DEKBETCITY`، `DEKINCITY`، `DEKBARBETCITY`، `DEKBARINCITY`، `DEKBACHBETCITY`، `DEKBACHINCITY`)
- `POSTBAR`: پست بار (سرویس `POSTBAR_EXPRESS`)
- `POSTEX_EXPRESS`: پستکس وان (سرویس‌های `DGX_GOLD`، `DGX_STANDARD`، `DGX_BUSINESS`)
- `COREPOSTING`: پستکس وان درون‌شهری و عادی (سرویس‌های `COREPOSTING_GOLD`، `COREPOSTING_CARD`)
- `BAREXPRESS`: باراکسپرس (سرویس‌های `T2D`، `T2T`)

`MAHEX` فقط در نمونهٔ فیلد `GetQuotesCourier` سند رسمی آمده و در فهرست سرویس‌های فعال نیست؛ نباید در تنظیمات استفاده شود. کد مستقلی به نام `POSTEX` وجود ندارد و معادل واقعی آن `POSTEX_EXPRESS` است. جدول کامل در بند ۹.۳.

### ۷.۳. کدهای وضعیت در پارسر سامانه (`PostexStatusParser`)
معیار قطعی، «کد والد» (`parentCode`) است که فقط نُه مقدار دارد و همهٔ ۶۶ کد سرویس زیرمجموعهٔ یکی از این نه‌اند (فهرست کامل در بند ۹.۲). فیلد `name` یکتا نیست — چهار کد نام `CANCELED` و سه کد نام `DELIVERED` دارند — پس تطبیق بر پایهٔ متن یا نام ممنوع است و باید با کد عددی انجام شود.

| کد والد | نام | عنوان | نگاشت بای‌مانی |
| :--- | :--- | :--- | :--- |
| 1 | `PAYMENT_PENDING` | در انتظار پرداخت | `InTransit` |
| 2 | `IN_PROCESS` | در حال بررسی | `InTransit` |
| 3 | `IN_TRANSIT` | در مسیر | `InTransit` |
| 4 | `DELIVERED` | تحویل شده | `Delivered` |
| 5 | `RETURNED` | برگشتی | `Returned` |
| 7 | `PICKED_UP` | جمع آوری | `InTransit` |
| 8 | `CANCELED` | لغو شده | `Returned` |
| 9 | `READY_TO_SEND` | آماده ارسال | `InTransit` |
| 10 | `OTHERS` | سایر | بدون تغییر وضعیت؛ فقط ۱۱۳۰۴ و ۱۱۳۰۵ هشدار پایدار |

- تحویل: والد `4` و فرزندان `11106`، `11202`، `11301` (تحویل تأییدشده) و `11303` (تسویه شد).
- بازگشت و عدم تحویل: والد `5` و فرزندان «امتناع گیرنده» (`11203`)، «عدم امکان تحویل» (`11215`)، «عدم حضور گیرنده» (`11225`) و «بازگشت به فرستنده» (`11249`)؛ همچنین والد `8`. `11305` فرزند والد ۵ نیست (والدش در جدول ۹.۲ کد ۱۰ است).
- استثنای `InTransit` فقط `11311` (`DELIVERY_RETRY`، «شروع توزیع مجدد») است و حتی زیر والد تحویل، تحویل ثبت نمی‌شود. `11310` (`ROUTE_NOT_FOUND`) با والد ۸، یا بدون والد، `Returned` است؛ اگر والد آمده و ۸ نیست همان والد تصمیم می‌گیرد. تصمیم هرگز بر پایهٔ نام متنی نیست.
- والد ۱۰ وضعیت را عوض نمی‌کند. فقط `11304` و `11305` هشدار پایدار می‌سازند (حتی اگر با والد دیگری بیایند) و تحویل نمی‌شوند. بقیهٔ فرزندان والد ۱۰، مثل `11244`، نه هشدار پایدار می‌سازند و نه قلم `Preparing` را `Shipped` می‌کنند.

## ۸. نگاشت نیازمندی‌های سامانه ByeMoney به سرویس‌های پستکس

### ۸.۱. اسلایس الف: استعلام خودکار وضعیت (`SHIP-TRACKING`)
1. کلاینت `PostexTrackingClient` پیاده‌سازی پورت عمومی `ITrackingProviderClient` با کلید منبع `PostEx` است و با استعلام دوره‌ای از اندپوینت `GET /api/v1/parcels/{parcel-no}/status` آخرین وضعیت را می‌خواند. شناسهٔ ارجاع مرسوله (`providerParcelId`) برای این منبع اجباری است؛ مسیر جایگزین `GET /api/v1/tracking/events/{courier}/{tracking-code}` استفاده نمی‌شود.
2. با هدر `x-api-key` احراز هویت صورت می‌گیرد.
3. در صورت دریافت وضعیت `Delivered`، متد `PhysicalDeliverySyncService.SyncExternalAsync` وضعیت قلم کالا در بای‌مانی را به `Delivered` تغییر می‌دهد و شناسه تاریخ تحویل ثبت می‌شود. این متد به نام فروشنده وابسته نیست و واسط هر قلم را از منبع همان قلم انتخاب می‌کند.
4. اگر وضعیت مرسوله `Returned` شود، `CarrierReturnedAtUtc` یک‌بار و فقط روی قلم `Shipped` ثبت می‌شود (بدون تغییر `DeliveryStatus` و بدون برگشت نور)، از تأیید خودکار ۳۰روزه و از فهرست قابل‌تسویه خارج می‌ماند تا رسیدگی دستی ادمین. هشدار `11304`/`11305` هم فقط روی `Shipped` یک‌بار ثبت می‌شود و همان خروج از تحویل خودکار و تحویل همگام را دارد؛ `CarrierReturnedAtUtc` نمی‌سازد.

### ۸.۲. اسلایس ب: ساخت مرسوله با وب‌سرویس (`SHIP-TRACKING-B` — اجرا ۲۰۲۶-۱۱-۱۵)
ساخت از پورت عمومی `IShipmentProviderClient` و پیاده‌سازی `PostexShipmentClient` است (افزودن واسط بعدی فقط یک کلاینت تازه):
1. اول `GET /api/v1/parcels/custom-order-no/{custom-order-no}` برای idempotency؛ فقط ۴۰۴ یعنی مرسوله نیست و بعد `POST /api/v1/parcels/bulk`. خطای خواندن ساخت را شروع نمی‌کند. فراخوانی واسط بیرون از تراکنش و قفل انجام می‌شود: پیش از HTTP یک «رزرو کوتاه» (ستون `ShipmentRequestStartedAtUtc`، مهلت پنج دقیقه) در یک تراکنش کوتاه ثبت می‌شود و درخواست دوم تا انقضای رزرو ۴۰۹ می‌گیرد؛ نتیجه هم در یک تراکنش کوتاه دیگر ذخیره می‌شود. رزرو فقط با رد صریح پیش از ارسال یا پاسخ قطعی ناموفق آزاد می‌شود؛ در نتیجهٔ نامعلوم (تایم‌اوت، ۵xx، ۴۰۲ و بعد شکست خواندن) می‌ماند تا خودش منقضی شود و تلاش بعدی اول بخواند. بدین ترتیب تراکنش و قفل مشورتی در طول پاسخ کند واسط باز نمی‌مانند.
2. **فرستنده:** پروفایل مبدأ از `Postex:Origins[{shippingOriginId}]` (شناسهٔ فریزشدهٔ سبد، مشترک با استرپی؛ مثل `ramsar` با `city_id=573`). سازگاری عقب‌رو: اگر `Origins` خالی باشد، `Postex:Sender` قدیمی به‌عنوان `ramsar` نقشه‌برداری می‌شود. برای `collection_type=pick_up` داشتن `lat`/`lon` معتبر در همین پروفایل اجباری است؛ نبودشان ساخت را پیش از `bulk` با پیام روشن متوقف می‌کند.
3. **گیرنده:** نسخهٔ ثابت آدرس سبد بای‌مانی؛ `city_id` همان کد حامل است که از جدول محل استرپی خوانده می‌شود (شناسهٔ فریزشده، یا برای سفارش قدیمی نام دقیق) و در بای‌مانی ذخیره نمی‌شود. `locality/cities/all` برای گیرنده خوانده نمی‌شود.
4. **بسته:** فقط عوامل فریزشدهٔ خرید (`ParcelFacts`) فرستاده می‌شود: `box_type_id` (۱…۱۲)، `length`/`width`/`height` سانتی‌متر هم‌خوان با همان جعبه، `total_weight` گرم، `total_value` ریال و `is_fragile`؛ `parcel_items` یک ردیف با `description` عنوان، `quantity` تعداد باقی‌مانده، `weight` وزن فریزشده و `price` ارزش فریزشده دارد. پیش‌فرض وزن/جعبه/ارزش حذف شده‌اند؛ نبود عوامل کامل (از جمله جعبه)، ساخت را پیش از فراخوانی واسط رد می‌کند. کوریر پیش‌فرض `IR_POST`/`EXPRESS`، پرداخت `SENDER` و بدون `added_service` می‌ماند.
5. **`custom_order_no`:** `BM-{PurchaseId:N}`؛ کلید در سطح بای‌مانی یکتا است چون پستکس تکرار را مسدود نمی‌کند.
6. **خروجی:** `parcel_no` → `ProviderParcelId`؛ بارکد غیرماسک → `TrackingCode`. فقط با بارکد غیرماسک خرید `Shipped` می‌شود. شمارهٔ داخلی یا بارکد ستاره‌ای خرید را `Preparing` نگه می‌دارد، شناسهٔ ارجاع و تعداد لحظهٔ ساخت (`CarrierParcelQuantity`) را ذخیره می‌کند و به ادمین می‌گوید کد پستی هنوز نیامده. خواندن دوره‌ای بعدی همان مرسوله، با آمدن بارکد واقعی، وضعیت را `Shipped` می‌کند (فقط اگر تعداد باقی‌مانده با تعداد لحظهٔ ساخت یکی باشد) و در همان مرحله `Delivered` نمی‌کند. پاسخ `402` یا والد `1` (`PAYMENT_PENDING`) خطای دامنه برنمی‌گرداند: مرسوله نه ارسال‌شده است و نه شکست؛ شناسهٔ مرسوله و نشان `CarrierPaymentPendingSinceUtc` روی همان قلم `Preparing` ذخیره می‌شود و پاسخ ۲۰۰ با نتیجهٔ `PendingPayment` و پیام راهنما برمی‌گردد. تکرار همان کلید مرسولهٔ دوم نمی‌سازد. `collection_type` از درخواست ادمین است: `pick_up` با `ready_to_accept=true`، یا `courier_drop_off` بدون اعلام پیک و بدون شناسهٔ دفتر.
7. **خطای اعتبارسنجی:** `ExtractErrorMessage` علاوه بر `Message`/`message`/`title`، خطاهای فیلدی `errors` و `invalid_fields` را با نام فیلد و پیام‌ها در خطای دامنه نشان می‌دهد.
8. **بررسی وضعیت (`POST /shipments/refresh`):** مرسوله با همان `custom-order-no` خوانده می‌شود، بیرون از قفل و بدون اثر مالی. نتیجه یکی از این‌هاست: همچنان `PAYMENT_PENDING` (نشان می‌ماند)، پذیرفته با بارکد واقعی و تعداد هم‌خوان (`Shipped`)، پذیرفته بدون بارکد (نشان پاک و در انتظار بارکد)، یا «مرسوله نیست» که ارجاع را پاک می‌کند تا ساخت دوباره مجاز شود. خطای خواندن تغییری نمی‌دهد. بررسی خودکار چرخهٔ همگام‌سازی هم قلم‌های `Preparing` دارای شناسهٔ مرجع را می‌بیند و با آمدن بارکد واقعی ارتقا می‌دهد؛ مرسولهٔ حل‌نشده در انتهای صف این چرخه قرار می‌گیرد تا جلوی قلم‌های تازه را نگیرد. `mark-ready` در این مرحله پیاده نشده است (رفتارش روی مرسولهٔ پرداخت‌نشده تأیید نشده) و پرداخت/آماده‌سازی دستی در پنل پستکس می‌ماند.

| `GET /api/v1/locality/cities/to/all` | ۱.۵ کیلوبایت | خروجی دقیقاً یکسان با مسیر مبدأ |
| `GET /api/v1/locality/countries` | ۱ ردیف | فقط `[{"country_code":"1","country_name":"مصر"}]` |

ده شهر پیش‌فرض مسیرهای `from/all` و `to/all`: تهران (1)، شیراز (409)، اصفهان (175)، مشهد (259)، اراک (107)، همدان (286)، تبریز (74)، ساری (555)، قم (446)، ری (114). فهرست کامل پستکس فقط از `cities/all` یا `cities/{province-code}` است، نه از این دو مسیر. شهر گیرندهٔ مرسولهٔ بای‌مانی از این فهرست پیدا نمی‌شود؛ کد حامل از جدول محل استرپی خوانده می‌شود (D20 بند ۱۱).

### ۹.۸. موارد مسدود بدون کلید — نیازمند کلید معتبر

این فراخوانی‌ها بدون کلید `401` می‌دهند. با کلید معتبر در بخش ۱۰ اجرا و پاسخ واقعی ثبت شده‌اند؛ فقط خواندن مرسولهٔ تحویل‌شدهٔ قبلی ممکن نشد چون حساب مرسولهٔ قدیمی نداشت.

| مورد | اندپوینت | پرسش بی‌پاسخ |
| :--- | :--- | :--- |
| قیمت واقعی | `POST /api/v1/shipping/quotes` | ساختار پاسخ `GetShippingQuotesResult`، واحد مبالغ، تفکیک کرایه و مالیات |
| وضعیت مرسوله | `GET /api/v1/parcels/{parcel-no}/status` | شکل پاسخ پارسر، وجود `tracking_no` |
| جزئیات مرسوله | `GET /api/v1/parcels/{parcel-no}` | محل دقیق `tracking_no` و فیلدهای تاریخ |
| گزارش رویدادها | `GET /api/v1/tracking/report` | صحت ساختار `StatusChangeReport` حدس زده‌شده در بند ۶.۵ |
| ثبت مرسوله | `POST /api/v1/parcels/bulk` | شکل پاسخ، محل `parcel_no`، اینکه `tracking_no` همان لحظه صادر می‌شود یا نه |
| تکرار ثبت | همان مسیر با `custom_order_no` تکراری | خطا یا مرسولهٔ دوم — تعیین‌کنندهٔ طراحی idempotency |
| خواندن با شناسهٔ سفارش | `GET /api/v1/parcels/custom-order-no/{no}` | امکان الگوی «اول بخوان، بعد بساز» |
| لغو | `POST /api/v1/parcels/cancel-request/{parcel-no}` | شکل پاسخ و وضعیت پس از لغو |
| خطای اعتبارسنجی | `POST /api/v1/parcels/bulk` با بدنهٔ ناقص | قالب خطای اعتبارسنجی و اجباری بودن واقعی `national_code` و `city_id` |

بررسی این موارد فقط با کلید معتبر و در محیط آزمایشی پستکس انجام شود؛ در غیر این صورت یک مرسولهٔ واقعی ساخته می‌شود.

### ۹.۹. ناسازگاری‌های سرویس (برای پارسر و مدل‌سازی)

1. **کد ۱۱۲۵۱** والد `0` دارد که در فهرست کدها وجود ندارد، و عنوان و توضیحش خالی است.
2. **کد ۱۱۱۱۶** مقدار `name` آن `Send by post` با فاصله است، برخلاف قاعدهٔ `SCREAMING_SNAKE_CASE` بقیه.
3. **`name` یکتا نیست:** `CANCELED` چهار بار (کدهای 8، 11216، 11228، 11307) و `DELIVERED` سه بار (4، 11106، 11202). تطبیق فقط با کد عددی مجاز است.
4. **والد و معنای عنوان هم‌راستا نیستند:** `11311` (`DELIVERY_RETRY`) زیر «تحویل شده» و `11310` (`ROUTE_NOT_FOUND`) زیر «لغو شده» است.
5. **سبک نام‌گذاری یکدست نیست:** `common` و `statuses` از `camelCase` و `boxes` و `locality` از `snake_case` استفاده می‌کنند؛ مدل‌های C# نباید از یک قاعدهٔ واحد برای نگاشت استفاده کنند.
6. **قالب پوشش پاسخ متفاوت است:** `shipping-methods` پاسخ را در `data` می‌پیچد، بقیهٔ مسیرهای عمومی آرایهٔ خام برمی‌گردانند.
7. **قالب خطا با قالب دادهٔ موفق یکسان نیست:** خطاها `{"IsSuccess", "Message"}` با حروف بزرگ برمی‌گردانند، در حالی که دادهٔ موفق `snake_case` است؛ مدل خطا باید جدا تعریف شود.

### ۱۰.۱. استعلام هزینه — پاسخ کامل

درخواست معتبر باید `courier` داشته باشد. بدون آن: `400` و `invalid_fields.courier = ["The Courier field is required."]`.

### ۱۰.۲. ثبت مرسوله (`POST /api/v1/parcels/bulk`)

قالب پاسخ موفق سطح HTTP برابر `200` است، ولی موفقیت واقعی فقط با `result[].isSuccess` مشخص می‌شود:

```json
{
  "order_no": 1182069,
  "pick_up_price": 0,
  "shipping_price": 0,
  "total_price": 0,
  "result": [
    {
      "isSuccess": false,
      "message": "خطا در هنگام ثبت مرسوله: در شهر مبدا نماینده ای تعریف نشده است",
      "data": { "custom_order_no": "BM-BAD-002", "custom_reference_no": null }
    }
  ]
}
```

**رفتار حساس در خطای پرداخت:** با موجودی ناکافی کیف پول، پاسخ `402` و بدنهٔ `{"IsSuccess":false,"Message":"موجودی کیف پول شما برای ثبت این مرسوله کافی نیست"}` برمی‌گردد، ولی مرسوله **واقعاً ساخته می‌شود** و در وضعیت `PAYMENT_PENDING` (کد ۱۰۰۰۰) می‌ماند. در این حالت پاسخ هیچ `parcel_no` ندارد؛ شناسه فقط با خواندن `custom-order-no` به دست می‌آید.

**تکرار (idempotency):** ارسال دوبارهٔ همان بدنه با همان `custom_order_no` منجر به ساخت مرسولهٔ **دوم** شد (نه خطا). پس پستکس تکرار را مسدود نمی‌کند و `custom-order-no` هم آخرین رکورد را برمی‌گرداند.

```json
  "tracking_number": "**********",

```

- `status_code` همان کد ردیف جدول ۹.۲ و `parent.code` همان کد والد است؛ پایهٔ پارسر همین دو فیلد است، نه `status_name`.
- `tracking_number` تا قبل از پرداخت/پذیرش با ستاره ماسک است (`**********`)؛ یعنی رهگیری بر پایهٔ بارکد تا زمانی که مرسوله پرداخت نشود قابل اتکا نیست. بارکد ستاره‌ای و شمارهٔ داخلی `parcel_no` کد قابل‌استفاده نیستند و خرید را «ارسال‌شده» نمی‌کنند.
- `parcels/statuses/query` با بدنهٔ `{"parcel_no": [...]}` آرایه‌ای از همین ساختار برمی‌گرداند.

### ۱۰.۴. فهرست مرسولات

```json
{ "page_index": 1, "page_size": 3, "total_count": 0, "total_pages": 0, "index_from": 0, "items": [], "has_prev_page": true, "has_next_page": false }
```

`has_prev_page` در صفحهٔ اول هم `true` است؛ ناوبری صفحه باید از `total_pages` و `page_index` محاسبه شود. هر ردیف `items` شکل مسطح دارد: `order_no`، `parcel_no`، `from`، `to`، `parcel_properties`، `shipment{ courier, tracking{ barcode, tracking_number, tracking_url }, shipping_rate{ amount, vat, total_amount }, created_at }`، `current_status`، `created_at_local` (تاریخ جلالی)، `value_added_service`.

### ۱۰.۵. خواندن با شناسهٔ سفارش

`GET /api/v1/parcels/custom-order-no/{no}` دو رفتار مشخص دارد:

- اگر مرسوله وجود داشته باشد، `200` و **جزئیات کامل** همان مرسوله را می‌دهد (همان شکل فهرست به‌همراه `parcel_no`، `current_status`، `shipment[].tracking`، `pricing_details`، `box_size` و `value_added_service`).
- اگر وجود نداشته باشد، `404` با پیام فارسی `مرسوله ای با چنین مشخصاتی یافت نشد` می‌دهد.

یعنی «اول بخوان، بعد بساز» روی همین کد قابل پیاده‌سازی است، با دو شرط: وجود مرسوله را از کد `200` تشخیص بدهید (نه از خالی بودن بدنه)، و بدانید وقتی چند مرسوله با یک `custom_order_no` وجود دارد، تنها **آخرین** رکورد برمی‌گردد — پس یکتایی `custom_order_no` را باید خودمان تضمین کنیم.

### ۱۰.۶. قواعد اعتبارسنجی واقعی (متفاوت با سند)

1. `contact.telephone_no` در هر دو طرف (`from` و `to`) **اجباری است**، هرچند سند فقط `first_name`، `last_name` و `mobile_no` را اجباری می‌داند.
2. `contact.national_code` اجباری **نیست**؛ اگر ارسال نشود خود سرویس مقدار `0101111101` می‌گذارد — برای سفارش واقعی باید کد ملی مشتری صریحاً فرستاده شود.
3. `location.city_id` اگر حذف شود، خطای اعتبارسنجی نمی‌دهد؛ در عوض `isSuccess: false` با پیام «در شهر مبدا نماینده ای تعریف نشده است» برمی‌گرداند.
4. `telephone_no` در رکورد ذخیره‌شده با `mobile_no` جایگزین می‌شود؛ یعنی تلفن ثابت واقعاً ذخیره نمی‌شود.
5. شکل رکورد ذخیره‌شده: `parcel_no` عدد ۱۳ رقمی (مثل `1319906676294`)، `order_no` عدد ۷ رقمی (مثل `1182071`)، `tracking` ماسک‌شده، `created_at` به وقت محلی تهران و **بدون** آفست (مثل `2026-11-15T15:51:26.6`). این مقدار را نباید `UtcNow` فرض کرد.

### ۱۰.۷. چهار قالب خطای متفاوت (مهم برای کلاینت)

| حالت | کد | بدنه |
| :--- | ---: | :--- |
| کلید نامعتبر/غایب | 401 | `{"IsSuccess":false,"Message":"..."}` — `PascalCase` |
| اعتبارسنجی مدل (bulk) | 400 | `{"type","title","status","errors":{"Parcels[0].To.Contact.TelephoneNo":["..."]},"traceId"}` |
| اعتبارسنجی کسب‌وکار (quotes) | 400 | `{"invalid_fields":{"courier":["..."]},"isSuccess":false,"message":"خطا در داده های ورودی"}` |
| خطای سرویس جانبی (time-windows) | 400 | `{"timestamp","status","error","path"}` — سبک Spring |
| مرسولهٔ ناموجود | 404 / 400 | `GET /parcels/{no}` → 404 با پیام فارسی؛ `GET /parcels/{no}/status` → 400 با `Parcel 999999999 not found` |

### ۱۰.۸. محدودیت‌های عملیاتی که در سند نبود

- **لغو در وضعیت پرداخت‌نشده ممکن نیست:** `POST /parcels/cancel-request/{no}` در `PAYMENT_PENDING` پاسخ `400` با پیام «مرسوله امکان درخواست کنسلی ندارد.» می‌دهد.
- **حذف وجود ندارد:** `DELETE /parcels/{no}` پاسخ `405` می‌دهد؛ مرسولهٔ پرداخت‌نشده از طریق API قابل پاک‌سازی نیست.
- **سرویس وب‌هوک در دسترس نیست:** `GET /api/v1/events` پاسخ `502` با متن `Resource temporarily unavailable (webhooks-api:8080)` و `GET /api/v1/events/1` پاسخ `404` متنی می‌دهد.
- **گزارش رهگیری:** با بازهٔ ۴۸ ساعته `200` و آرایهٔ خالی برگشت؛ ساختار `StatusChangeReport` هنوز دیده نشده و در ۹.۸ درست علامت خورده است.
- **`shipping-methods` با کلید** همان ۱۸ سرویس حالت بدون کلید را می‌دهد؛ داده‌اش وابسته به حساب نیست.

### ۱۰.۹. اثر روی طراحی ماژول `PostexIntegration`

1. **پاسخ `402` را «ثبت نشده» فرض نکنید:** احتمال ساخت مرسولهٔ پرداخت‌نشده وجود دارد. پس از هر پاسخ غیرقطعی (نه فقط ۲۰۰)، با `custom-order-no` وضعیت را تطبیق دهید.
2. **پاسخ `bulk` شناسه نمی‌دهد؛** `parcel_no` را باید از خواندن `custom-order-no` یا فهرست بگیرید، نه از بدنهٔ ثبت.
3. **بدون idempotency سمت پستکس،** پیش از هر ارسال باید «اول بخوان، بعد بساز» اجرا شود و `custom_order_no` یکتا در سطح بای‌مانی تضمین شود؛ وگرنه یک قلم کالا دو مرسوله می‌سازد.
4. **موفقیت را از `result[].isSuccess` بگیرید،** نه از کد HTTP.
5. **زمان‌ها محلی‌اند:** `created_at` را با آفست تهران تفسیر کنید و در دیتابیس بای‌مانی به UTC تبدیل کنید.
6. **عدم اتکا به بارکد تا قبل از پرداخت:** هر نمایش رهگیری برای مرسولهٔ پرداخت‌نشده باید حالت «در انتظار پرداخت» را جدا نشان دهد.
7. **مرسولهٔ پرداخت‌نشده دادهٔ پایدار است، نه خطا:** شناسهٔ `parcel_no` و نشان زمانی «در انتظار پرداخت» روی همان قلم ذخیره می‌شود (وضعیت `Preparing` می‌ماند) و بعد از شارژ کیف پول واسط با «بررسی وضعیت» دوباره خوانده می‌شود؛ نتیجهٔ خواندن یکی از چهار حالت پرداخت‌نشده، پذیرفته با بارکد (ارسال‌شده)، پذیرفته بدون بارکد، یا «مرسوله نیست» است.
8. **رزرو ساخت اجباری است:** پستکس تکرار را مسدود نمی‌کند، پس رزرو کوتاه در دیتابیس و مهلت بیشتر از جمع تایم‌اوت‌های کلاینت لازم است؛ نتیجهٔ نامعلوم رزرو را آزاد نمی‌کند و تلاش بعدی اول می‌خواند.
9. **تعداد لحظهٔ ساخت باید بماند:** با کاهش تعداد پس از ساخت مرسوله، ارتقای خودکار به `Shipped` ممنوع است؛ وگرنه مرسوله‌ای با تعداد قدیمی «ارسال‌شده» ثبت می‌شود.
